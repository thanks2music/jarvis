# claude-docs-sync — ClaudeCode 公式ドキュメント鮮度同期スキル

JARVIS リポジトリの `docs/` は ClaudeCode の機能解説ドキュメント群である。ClaudeCode は高頻度で
バージョンアップされるため、公式の最新情報を調査し、新機能のドキュメント化と既存ドキュメントの
更新を行うことで「鮮度を保つ」のがこのスキルの役割である。

このスキルは **ファイルを書き換える副作用を持つ**。そのため必ず「調査 → 差分レポート → BOSS の
承認 → 反映」という承認ゲートを挟む。承認を得ずにファイルを書き換えてはならない。なぜなら、公式
情報の解釈や「新規ファイルにすべきか追記すべきか」の判断には BOSS の意図が関わるため、AI が独断で
リポジトリを変更すると BOSS の主体性を損なうからである (このリポジトリの「AI は手段、人間が主体」
原則)。

## 0. 前提ガード (最初に必ず実行)

このスキルは JARVIS リポジトリ専用である。誤起動を防ぐため、最初に以下を確認する。

1. カレントディレクトリに `docs/` が存在するか
2. `docs/best-practices.md` と `docs/skills.md` が存在するか (JARVIS リポジトリの指紋)

いずれかを満たさない場合は、ファイルを一切操作せず次のように報告して終了する:

> このスキルは JARVIS リポジトリ (docs/ に ClaudeCode 機能解説を持つリポジトリ) 専用です。
> カレントディレクトリでは対象ドキュメント群が見つかりませんでした。

`pwd` と `ls docs/` で確認できる。

## 1. 全体フロー

```
[起動] → 前提ガード → フェーズ1: 調査と差分検出
                          ↓
                   差分レポートを出力・要約提示
                          ↓
                   ★ BOSS の承認 (自然言語) ★ ← 承認なしに先へ進まない
                          ↓
                   フェーズ2: 承認項目のみ反映 → 連動更新 → 報告
```

差分がゼロなら、フェーズ1 の末尾で「ドキュメントは最新です」と報告し、状態ファイルの調査日だけ
更新して終了する (フェーズ2 に進まない)。

詳細な手順とチェックリストは `references/workflow.md` を参照する。**フェーズに入る前に必ず一読する**。

## 2. フェーズ1: 調査と差分検出

### 2-1. 今日の日付と状態を確認する

- まず今日の日付を確認する (`date +%Y-%m-%d`)。レポート名・タイムスタンプに使う。
- 状態ファイル `docs/.docs-sync-state.json` を読む。前回スキャン日・把握済みバージョン/機能・
  `doc ↔ 出典URL` のマッピングが記録されている。存在しなければ初回として扱う。
  スキーマは `references/state-schema.md` を参照する。

### 2-2. 対象ドキュメントを動的に把握する

`docs/*.md` を Glob で走査して対象一覧を得る (ファイル名はハードコードしない。将来 docs が増減して
も追従するため)。各ファイル冒頭の `> 出典: <URL> (YYYY-MM-DD時点)` / `> 最終更新: YYYY-MM-DD` を
読み、鮮度判定の基準と「その doc が依拠する公式 URL」を抽出する。

### 2-3. 公式ソースを調査する (SubAgent に並列ファンアウト)

調査対象が広いため、調査は複数の SubAgent に並列委任する。Opus は明示的に指示しないと SubAgent を
控える傾向があるため、**「同一ターンで複数 SubAgent を spawn せよ」と明示的に意図して呼び出す**。
1 応答で完結する小さな確認まで SubAgent に委ねる必要はないが、この調査は横断的で重いため委任が適切。

推奨する分担 (3 つの SubAgent を同時に起動):

1. **新機能検出担当**: `https://code.claude.com/docs/en/whats-new` を起点に、新コマンド・新機能・
   新しい設定・廃止予定を洗い出す。既知エントリ (状態ファイル) と比較し「新規」のみ抽出。
2. **既存ドキュメント陳腐化チェック担当**: 各 doc の「> 出典 URL」を再フェッチし、現行の公式記述と
   doc の記述を照合。バージョン番号・廃止 API・仕様変更・新コマンドのズレを抽出。
3. **モデル/ブログ担当**: `https://anthropic.com/news` (新モデル発表、例: Opus 4.8) と
   `https://claude.com/blog` (ベストプラクティス系) を調査。best-practices.md / harness.md に
   影響する変更を抽出。

各 SubAgent には「要約 + 出典 URL のみ返せ。本文を丸ごと貼るな」と指示し、メインコンテキストを汚さ
ない。SubAgent への具体的な指示テンプレートは `references/subagent-prompts.md` にある。

### 2-4. 調査ルール (厳守)

- **正ソースは英語版 (en)**。`code.claude.com/docs/en` と英語ブログ/発表を一次情報とする。日本語版
  は翻訳ラグがあるため参考に留め、記述が食い違う場合は en を採用する。
- ツール優先順位: **Context7 / DeepWiki を最初に使い**、不足を WebSearch / WebFetch で補完する
  (code.claude.com は Context7 に十分入っていないことが多く、WebFetch/WebSearch が主になる)。
- **公式一次情報のみ採用**。二次情報 (Qiita / Zenn / 個人ブログ等) をベストプラクティスの根拠に
  しない。
- 全ページ全走査はしない。whats-new + 既存 docs が依拠するページ + モデル/ブログに範囲を絞る。
- 公式 (en) で裏が取れない情報はドキュメント化しない (憶測禁止)。
- 公式ソース間で仕様が食い違う場合は、選択肢付きで BOSS に報告し判断を仰ぐ。

### 2-5. 差分を分類する

検出した差分を 2 種類に分類する。

- **【新機能】** 既存 docs のどのファイルにも対応しない新コマンド/機能
- **【更新必要】** 既存ドキュメントの記述が古い箇所 (バージョン・仕様・廃止 API・新モデル等)

新規ドキュメント化 vs 既存ファイル追記の判定基準:

- 変更を **1 文で説明できる** 小さな機能追加/仕様変更 → 既存の該当ファイルに **追記**
- **独立した大型機能** (例: Agent Teams のような新概念) → `docs/` に **新規ファイル** を作成

判断に迷う中間ケースは、レポート上で「新規 / 追記どちらの案か」を明示し、BOSS の判断に委ねる。

### 2-6. 差分レポートを出力する

`docs/sync-reports/YYYY-MM-DD-docs-sync.md` に出力する (本リポで git 管理される)。`sync-reports/`
が無ければ作成する。各項目に **通し番号** を振る (承認時に「3 番と 5 番は却下」と指定できるように)。
レポートの構成テンプレートは `references/report-template.md` にある。

出力後、レポートの要約を会話に提示し、BOSS の承認を自然言語で受ける。「全部反映」「1・2 番のみ」
「3 番は却下」等の指示を解釈する。**承認なしにフェーズ2 へ進まない。**

## 3. フェーズ2: 承認後の反映

承認された項目のみ反映する。詳細手順は `references/workflow.md` の「フェーズ2」を参照する。要点:

1. **モデル世代の更新は追記方式**。最新世代を追記しつつ旧世代の記述も履歴として残す
   (harness.md のモデル世代テーブルのように「何がどう変わったか」を追える形を維持する。常に
   最新だけに置き換えると、BOSS が進化の経緯を学べなくなるため)。
2. **新規ドキュメント作成時の連動更新** (忘れやすいので必ず実施):
   - `README.md` の目次テーブル (**英語版・日本語版の両方**)
   - `CLAUDE.md` の「ドキュメント構造」ツリーと「ドキュメント参照」リスト
   - ※ 既に CLAUDE.md の目次が実態とドリフトしている場合 (未記載ファイルがある等) は、その是正も
     レポートに含めて承認を得た上で行う。
3. 更新したファイルの `> 最終更新` / `(YYYY-MM-DD時点)` を当日日付に更新する。
4. `docs/.docs-sync-state.json` を更新する (今回の調査日・把握済み機能・doc↔URL マッピング)。
5. 変更点サマリと、採用した出典 URL 一覧を報告する。

## 4. best-practices.md の扱い (重要文書)

`docs/best-practices.md` は ClaudeCode 公式を精読して作成した重要文書であり、**他の docs と
同様に更新対象に含める**。かつては「編集対象外 (聖域)」指定があったが、ベストプラクティスは継続的に
変化するため CLAUDE.md で撤廃済み (CLAUDE.md「ベストプラクティスドキュメントの更新方針」を参照)。

ただし重要文書のため、更新時は以下を徹底する:

- 変更時は必ず差分レポートに含め、承認を得る (他ファイルより慎重に確認する)。
- 公式一次情報 (英語版) を根拠とし、出典 URL を明記する。
- モデル世代の記述は置換でなく追記 (履歴併存) とする (No.3 のモデル世代追記方針と同じ)。

## 5. 記述規約 (このリポジトリ固有・厳守)

新規・更新いずれのドキュメントも以下に従う。詳細・具体例は `references/doc-conventions.md` を参照。

- すべて **日本語** で記述する。
- 文体は **常体 (だ・である調)** で統一する。
- 技術用語 (ClaudeCode, MCP, GitHub 等) は英語表記を維持する。
- 冒頭に `> 出典: <公式URL> (YYYY-MM-DD時点)` を必ず置く。
- 新規ファイル名は **kebab-case** (例: `docs/agent-teams.md`)。
- 既存ドキュメントのトーン・テーブル構成・章立てスタイルを踏襲する (浮かないように)。
- 末尾に「関連ドキュメント」セクションを置き、相互リンクを張る。

## 6. 制約 (全フェーズ共通)

- フェーズ1 の承認を得ずにファイルを書き換えない。
- **git commit / push はしない**。変更はワーキングツリーに留め、BOSS に報告する (このリポジトリは
  個人開発スコープだが、コミット判断は BOSS に委ねる)。
- 憶測でドキュメント化しない。公式 (en) で裏が取れた情報のみ。
- 情報源間で仕様が食い違う場合は、選択肢付きで BOSS に報告する。
