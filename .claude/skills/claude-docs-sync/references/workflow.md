## フェーズ1: 調査と差分検出

### チェックリスト

- [ ] 前提ガード通過 (`docs/` と JARVIS 指紋ファイルの存在確認)
- [ ] 今日の日付を取得 (`date +%Y-%m-%d`)
- [ ] `docs/.docs-sync-state.json` を読む (なければ初回)
- [ ] `docs/*.md` を Glob で走査し対象一覧を取得
- [ ] 各 doc 冒頭の `> 出典` / `> 最終更新` を抽出し `doc ↔ 出典URL` を把握
- [ ] SubAgent プロンプトのプレースホルダーを state ファイルの実値に展開し、**`<` / `>` で囲まれた未展開プレースホルダーが残っていないか確認** (残っていると SubAgent が空リストを「既知」と解釈し、全件サイレントに「既知 = 更新不要」と誤判定するため)
- [ ] 3 つの調査 SubAgent を**同一ターンで**起動 (新機能 / 陳腐化 / モデル・ブログ)
- [ ] 各 SubAgent の結果 (要約 + 出典 URL) を統合
- [ ] 差分を【新機能】【更新必要】に分類
- [ ] 各【新機能】を「新規ファイル」か「既存追記」か判定 (1 文基準)
- [ ] `docs/sync-reports/YYYY-MM-DD-docs-sync.md` に通し番号付きで出力
- [ ] レポート要約を会話に提示
- [ ] 差分ゼロなら「最新です」報告 + 状態ファイル調査日のみ更新 → 終了

### 初回実行 (状態ファイルが無い) の注意

初回は「前回からの差分」が取れないため、全 doc の出典 URL を再フェッチして現行公式と照合する
フルスキャンになる。時間がかかる旨を BOSS に一言伝えてから着手する。完了後、状態ファイルを新規
作成して以降の差分検出の基準を作る。

### CLAUDE.md ドリフトの検出

`docs/*.md` の実在ファイルと、CLAUDE.md の「ドキュメント構造」ツリー/「ドキュメント参照」リストを
突き合わせ、**未記載のファイル**や**消えたファイルへの参照**があれば「ドリフト」として差分レポート
に含める (公式情報の変化とは別カテゴリだが、ドキュメント整合性の維持はこのスキルの責務)。

## 承認ゲートの扱い方

- レポートの要約を提示したら、BOSS の応答を待つ。**勝手に反映へ進まない。**
- 承認の解釈例:
  - 「全部反映して」→ 全項目を採用
  - 「1, 2, 4 番だけ」→ 該当番号のみ採用、他は今回見送り
  - 「3 番は却下、あとはOK」→ 3 番以外を採用
  - 「5 番はこう直して」→ 指示に沿って案を修正し、再度その項目だけ確認
- 見送った項目は状態ファイルに「検出済みだが未反映」として記録してもよいが、次回再提示されるのが
  自然なので、無理に抑制しない (BOSS が再考できる方が良い)。

## フェーズ2: 承認後の反映

### チェックリスト

- [ ] 承認された項目のみを対象にする (却下・見送りは触らない)
- [ ] 【更新必要】: 該当箇所を Edit。モデル世代は**追記方式**で旧世代も残す
- [ ] 【新機能・追記】: 既存ファイルの適切なセクションに追記
- [ ] 【新機能・新規】: `docs/<kebab-case>.md` を作成 (記述規約に従う)
- [ ] 新規作成した場合、`README.md` の目次テーブル (英/日 両方) を更新
- [ ] 新規作成した場合、`CLAUDE.md` の「ドキュメント構造」ツリー + 「ドキュメント参照」リストを更新
- [ ] best-practices.md を更新する場合は特に慎重に差分確認 (重要文書のため。聖域指定は撤廃済み)
- [ ] 更新した全 doc の `> 最終更新` / `(YYYY-MM-DD時点)` を当日日付に更新
- [ ] **横断自己検証**: 修正した事実のキーワードで `docs/*.md` を grep し、旧記述の残存を確認・追加修正 (反映漏れ防止)
- [ ] `docs/.docs-sync-state.json` を更新 (調査日・把握済み機能・doc↔URL マッピング)
- [ ] 完了報告 (総合サマリ + ファイル別サマリ + 採用出典 URL)
- [ ] git commit / push はしない (報告のみ)

### モデル世代追記の具体例

best-practices.md / harness.md には Opus の世代別記述がある。新モデル (例: Opus 4.8) が出た場合:

- 悪い例: 「Opus 4.7」を全部「Opus 4.8」に置換 → 進化の経緯が消える
- 良い例: 既存の 4.7 記述を残し、4.8 の章/行/テーブル行を追記。差分 (何が変わったか) を明示

harness.md の「モデル世代によるハーネス進化のまとめ」テーブルのように、世代を行として積み増す形が
このリポジトリの既存スタイル。それに揃える。

## 完了報告テンプレート

```markdown
ドキュメント同期が完了しました。

## 総合サマリ
今回の同期で <事実誤り N 件・廃止仕様 M 件・新世代反映 K 件> を是正した。<全体を 1〜2 文で要約>。

## ファイル別変更サマリ
### docs/mcp-setup.md
- 古かった点: MCP スコープ保存先を settings.json と誤記。SSE を通常の選択肢として併記していた
- 公式最新: user/local とも `~/.claude.json`。SSE は deprecated (HTTP 推奨)
- 修正理由: 公式が「settings.local.json ではない」と明示。SSE 非推奨を明記
- 出典: https://code.claude.com/docs/en/mcp
### docs/best-practices.md
- 古かった点: <…>
- 公式最新: <…>
- 修正理由: <…>
- 出典: <…>
（… 変更した全ファイルを列挙 …）

## 横断自己検証の結果
- 修正キーワード <…> で `docs/*.md` を grep → 旧記述の残存なし (OK) / 残存 N 件を追加修正

## 見送った項目 (BOSS 判断 / スコープ外)
- N. (理由)

## 状態
- docs/.docs-sync-state.json を更新 (調査日: YYYY-MM-DD)
- 変更はワーキングツリーに留めています (commit はしていません)
```

> **ファイル別サマリの書き方**: BOSS は「どのファイルに何が起き、何が古く、最新推奨は何で、なぜ直したか」を
> ファイル起点で把握したい。番号項目 (フェーズ1 のレポート) ではなく、**変更した実ファイルごと**に
> 「古かった点 / 公式最新 / 修正理由 / 出典」の 4 点を必ず書く。最後の総合サマリで全体像を 1〜2 文で示す。
